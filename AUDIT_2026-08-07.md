### Found afterwards, by running the audit tools against real data

Three findings that this report did not contain. They came out of actually running
`payouts:audit` and `wallet:check` against the local dataset (214 students, 380 invoices)
and production — which is the argument for those commands existing.

**A. `[CRITICAL]` The monthly cron would have paid production teachers 540.00 twice.**

```
RECORD  TEACHER            INVOICE  OWED  PAID  MONTHLY  QUEUED MONTHS
1126    youssef TIKO       842      270   270   90       2026-09, 2026-10
1127    Bader ET-THABITY   842      270   270   90       2026-09, 2026-10
1128    Majid FAYTI        842      270   270   90       2026-09, 2026-10
```

All three are **paid in full** and still carry queued months.
`processMonthlyPayments()` selected on `withUnpaidCurrentMonth()` alone and never asked
whether the teacher had already been paid. It would have fired on **1 September**.

**The wallet ledger does not catch this.** Its key is
`(teacher, invoice, month, reason, subject)`, so a credit for a month never previously paid
is a genuinely new row, not a duplicate. This was never the idempotency guard's shape.

Fixed in `dbc1b7d`: skip when `total_paid >= total_owed`, cap the credit at the outstanding
balance, and clear the stale month. Both branches log what they suppressed.
`payouts:clear-settled-months` (`30b3ec7`) drained the existing queues immediately rather
than waiting for the cron, so the exposure is gone by construction. **Production
double-pay exposure is now 0.00.**

**B. `[HIGH]` Subject percentage lookup was case-sensitive.**

`offers.percentage` is JSON keyed by subject name, read in five places as
`$offer->percentage[$subject] ?? 0`. PHP array keys are case sensitive.

Found in real data: membership 222, offer `2 BAC MATH`, percentages `{"Math": 60}`, teacher
assigned to subject `"math"`. One teacher, three possible answers depending on code path:

| | |
|---|---|
| What the offer says | **60%** |
| Create path (lookup missed → equal-distribution fallback) | 40% |
| Update path, before §6.7 was fixed | 0% — money clawed back |

All five call sites now go through `App\Support\OfferPercentages` (trimmed, lowercased,
whitespace-collapsed). Exact matches return unchanged, so correctly-spelled data is
untouched. Three of those sites were *reporting* paths, which would otherwise show 0% for a
teacher the wallet had actually paid.

**C. `[MEDIUM]` `payouts:audit`'s shortfall figure is not a payable amount.**

It reports `SUM(total_teacher_amount - total_paid_to_teacher)`, which mixes real drift with
months the cron simply has not reached yet. On the local dataset a reported **1,800.00** was
**240.00 not yet due** and **1,560.00 genuinely stranded**. Settling the headline figure
would have overpaid by 240.

`payouts:settle-stranded` (`4a61e1b`) splits them and pays only the stranded part, through
the ledger, dry-run by default. Applied locally: shortfall 1,800.00 → 240.00, overpaid
stayed at 0, `wallet:check` still reconciles. **Production had nothing stranded**, so
nothing was paid there.

> A test caught that the obvious `'settle-stranded'` idempotency marker overflows the
> `varchar(7)` `month` column, which would have aborted a live settlement partway through.

### Deliberately not done, and why

- **§8.9 `$hidden` on student medical fields.** `StudentForm.jsx` actively edits
  `hasDisease`, `diseaseName` and `medication`; hiding them globally would break the
  student edit form. The exposure was addressed at the source instead — the list endpoint
  already whitelists via `transformStudentData`, and the membership pickers now project
  explicit columns. Revisit only alongside a frontend change.
- **§9.4 php-fpm `pm = dynamic`.** Needs traffic data to size correctly. `pm = static` at 5
  workers is not currently a bottleneck at 1.2 GB of 3.8 GB used.
- **§9.7 Brotli.** Needs `ngx_brotli` compiled into the nginx image. Worth doing on a
  future image rebuild; gzip at level 5 is already configured.
- **Historical payout drift.** Unchanged — it needs a product decision, not a code change.
  `payouts:audit` quantifies it.

### Still needs you

1. **Off-box backups.** The nightly backup runs, verifies and restores correctly, but the
   copies live on the same VPS. That protects against bad migrations, application bugs and
   accidental deletion — **not** against losing the box. The script has the off-box path
   written and commented; it needs a destination only you can choose:
   ```bash
   apt-get install -y rclone && rclone config
   echo 'OFFSITE_REMOTE=myremote:tikoschool-backups' >> /etc/tikoschool-backup.env
   systemctl start tikoschool-backup.service

2. **`SCHEDULE_HEARTBEAT_URL`.** Empty. Failures are logged, which is a real improvement

3. **`MAIL_MAILER=log`.** Still no real transport, so password-reset links land in the log

4. **69 Dependabot advisories** on the GitHub default branch. Untouched — `main` is a
   separate branch from `local`.
5. **`tikoschool_vide`.** The empty schema still sits beside the live one. The backup script
   now refuses to run against it, but nothing stops `DB_DATABASE` being pointed there.

## 2. Fix in this order

This is a sequence, not a ranking. Each step either stops an active threat or protects the one
after it.

| # | Action | Why this position | Effort |
|---|---|---|---|
| 01 | Close SSH: firewall, disable password auth and root login, install fail2ban | Under active attack. Nothing else matters if the box is taken. | ~30 min |
| 02 | Automated nightly DB backup, off-box | You have exactly one backup — the one taken today. | ~1 hr |
| 03 | **Connect the `wallet:check` alarm** (§6.0) | Cheapest item here, and it is what makes every money finding below *observable*. Doing 05 without this means you fix the bug but still cannot see the next one. | ~30 min |
| 04 | Re-throw `HttpExceptionInterface` ahead of the generic catch | **Must land before 05 is trusted** — see §5.5. | ~1 hr |
| 05 | Authorization across the unguarded route surface (§5.1) | 87 authenticated routes carry no further guard. Any teacher can delete any school's invoices today. | ~1–2 days |
| 06 | Route `TransactionController` wallet writes through `TeacherWalletService` | Latent ledger corruption; fires on next UI payout. | ~2 hrs |
| 07 | Fix the three money bugs in §6.6–6.8 | Two silently move real money; one is a one-line fallback. | ~3 hrs |
| 08 | Add `--queue=whatsapp,default` to the queue worker | Parent notifications have never been delivered. | ~5 min |
| 09 | Dashboard stats recompute + PHP-side pagination | The two things that break first as schools are added. | ~4 hrs |
| 10 | Reclaim resources: drop opcache JIT, prune build cache, log rotation, disable binlog | Buys back disk and cancels the self-defeating MySQL tuning (§8.8). | ~1 hr |

connected, so it has to be built before the money fixes rather than assumed behind them. Item 05
dropped below 04 for the same class of reason — an authorization fix that gets swallowed by a
`catch (\Exception)` is worse than no fix, because it looks done.

### 3.2 `[CRITICAL] [VERIFIED]` No automated backups of any kind

No cron, no systemd timer, no restic/borg/mysqldump schedule anywhere. The only backup in existence
is `/root/backups/tikoschool_2026-08-07_1039.sql`, taken during today's deploy.
`DEPLOYMENT_RUNBOOK.md` already calls this *"the single highest-value thing left on the
infrastructure list"* — it was never actioned.

A disk failure or bad migration right now loses 486 students, every invoice, and the wallet ledger.

**Fix.** Nightly `mysqldump --single-transaction --routines --triggers --no-tablespaces` to a
retained **off-box** location. Keep `--triggers`: `invoices` carries two offer-consistency triggers

complete but silently accepts offer/price mismatches — no migration will put them back, because it
is already recorded as run.

### 3.4 `[MEDIUM] [VERIFIED] [REVISED]` php container reserves 192 MB of its 512 MB for opcache

> **Revision 2 — this finding was wrong and has been downgraded from HIGH.** The original text
> claimed *"358 MB against a 512 MB cap (70%)"*. That number came from summing host-side RSS across
> the seven php processes, which counts the **shared 192 MB opcache+JIT segment once per process**.
> RSS is the wrong instrument here. The cgroup — the counter the OOM killer actually reads — says:
>
> ```
> tikoschool-php-1:  137 MiB / 512 MiB  =  26.75%
> ```
>
> There is roughly **375 MB of real headroom, not 150 MB.** The remedy below is still worth doing;
> the urgency is not. Credit to the peer review for catching the methodology error.

Container limits vs actual:

| Container | Limit | Actual | % |
|---|---|---|---|
| nginx | 128 MB | 3.73 MB | 2.9% |
| php | 512 MB | 136.7 MB (docker stats) / 358 MB (host RSS sum) | 27–70% |
| mysql | 1200 MB | 406.8 MB | 33.9% |
| redis | 128 MB | 3.27 MB | 2.6% |

`docker/php/www.conf` sets `pm = static`, `pm.max_children = 5`, and `php.ini` sets
`memory_limit = 256M` — a theoretical worst case of **1,280 MB against a 512 MB cap**. php-fpm,
Reverb *and* the queue worker share that one container, so an OOM kill takes websockets and
background jobs down with the web tier.

Additionally `opcache.memory_consumption = 128` + `opcache.jit_buffer_size = 64M` = **192 MB of
shared memory permanently reserved** inside that same 512 MB.

**Fix.** Drop `opcache.jit` and its 64 MB buffer — JIT's tracing mode helps CPU-bound numeric code;
a Laravel request is dominated by I/O, where the gain is low single-digit percent. Consider
`opcache.memory_consumption = 96`. Consider `pm = dynamic` (`start_servers=2, min_spare=1,
max_spare=3`) to release memory during the school's predictable overnight lull.

## 4. Is Docker right for this box?

**Verdict: keep it.** Measured, not assumed.

| Component | Resident | Verdict |
|---|---|---|
| `dockerd` | 390 MB | Real overhead |
| `containerd` | 42 MB | Real overhead |
| 4 × `docker-proxy` | ~30 MB | Real overhead |
| **Total** | **~460 MB** | **~12% of RAM** |
| Container CPU at rest | 0.13–1.07% | Negligible |

**Reasoning:**

- **12% of RAM is real but affordable.** 1.8 GB free, zero OOM events in 30 days, swap at 88 MB of
  4 GB. Going native reclaims memory you are not currently short of.
- **The entrypoint does genuine safety work.** `migrate --force` that aborts the deploy on failure
  (the `|| true` was deliberately removed), `config:cache` / `route:cache` / `view:cache`, and
  supervisor keeping php-fpm, Reverb, the queue worker and cron alive. Reproducing that natively
  means systemd units and a deploy script you must write, test and maintain.
- **You have a tested runbook and no ops team.** "Recreate the container" is a rollback story. A
  hand-managed box drifts, and drift produces 3 a.m. incidents.
- **Your bottleneck is 1 vCPU, not Docker.** A native migration does nothing for that.

**When to revisit:** if you add a second school and start seeing swap usage or OOM kills. The answer
then is a 2 vCPU / 8 GB VPS, not dropping Docker — that buys far more than 460 MB and costs a
fraction of the engineering time a native migration would.

`DOCKER_TO_NATIVE_MIGRATION.md` exists and plans the move. My recommendation is to shelve it.

## 6. Money correctness

The ledger design itself is sound. These are the paths that go around it — and, first, the reason
you would not find out.

### 6.0 `[CRITICAL] [VERIFIED] [ADDED IN REVISION 2]` The nightly ledger alarm reaches nobody

**This finding invalidates an assumption made throughout the first draft of this report.** Revision 1
stated three separate times that `wallet:check` "alarms at 04:30 the following morning", and used
that as the mitigating control which kept §6.1 at a tolerable risk level. That control is not
connected. Verified on the live server:

```
cron (inside the php container):
    * * * * * php /app/artisan schedule:run >> /dev/null 2>&1
                                             ^^^^^^^^^^^^^^^^^ stdout AND stderr discarded

bootstrap/app.php:71-74:
    $schedule->command('wallet:check')
        ->dailyAt('04:30')
        ->withoutOverlapping()
        ->onOneServer();
        ^ no ->onFailure(), no ->emailOutputOnFailure(), no ->pingOnFailure(), no ->appendOutputTo()

app/Console/Commands/CheckWalletLedger.php:
    Log:: calls = 0
```

The command reports drift through `$this->error()` and a non-zero exit code. Cron throws both away,
nothing hooks the failure, and the command never writes to the log. **A teacher's wallet can drift
from the ledger every night for a year and no human or system is told.**

`payouts:audit` runs daily on the same schedule and has the same problem.

This makes §6.1 **more** dangerous than originally rated, not less: the bypass is latent, but when it
fires there is nothing to surface it.

**Fix.** Any one of these closes it, in ascending order of effort:

1. Add `Log::error()` to `CheckWalletLedger` on the failure branch — the app already ships logs.
2. Chain `->emailOutputOnFailure(...)` once `MAIL_MAILER` is a real transport (currently `log`).
3. Chain `->pingOnFailure('https://...')` at a free uptime service — works today, no mail needed.
4. Stop discarding scheduler output: `>> /var/log/schedule.log 2>&1` instead of `/dev/null`.

Do at least (1) and (3). ~30 minutes, and it is what makes every other finding in this section
observable. It is item 03 in the fix queue for that reason.

### 6.1 `[CRITICAL] [CORRECTED]` The wallet ledger has a hole its own guard test cannot see

`TransactionController.php:1628` and `:1647`, inside `updateEmployeeBalance()`, called from

```php

```

The `+=` form walks straight past it. **The guard rail has a hole precisely the shape of the real
bug.**

It is also internally inconsistent: `revertEmployeeBalance()` (1664-1713), used by `destroy()` and

TeacherWalletService so they land in the append-only…"* and uses the service correctly. Within a

Also missing on this path: no `lockForUpdate()`, no wrapping `DB::transaction()`, no idempotency —

Checked against your data:

### 6.2 `[HIGH] [VERIFIED]` An undefined variable silently nulls the ledger's audit trail

`TeacherMembershipPaymentService.php:598`:

```php

### 6.8 `[MEDIUM] [VERIFIED] [ADDED IN REVISION 2]` The multi-subject ledger collision is latent, not safe

The idempotency key is `(teacher_id, invoice_id, month, reason)` — it does **not** include the
subject. If one teacher ever holds two subjects on the same membership, the second credit for that
invoice/month is silently rejected by the unique constraint and that teacher is underpaid, with no

Checked against live data: every membership currently assigns each teacher exactly one subject, so
this cannot fire today. **That is a property of your current data, not a guarantee of the design** —
nothing in the schema or the application prevents a two-subject assignment being created tomorrow.

**Fix.** Either add `teacher_subject` to the unique key, or add a validation rule that rejects
duplicate teacher entries on a membership. Until then, treat it as a documented constraint on how
memberships may be configured.

### 8.8 `[MEDIUM] [SOURCE]` MySQL is tuned for a machine you do not have

`docker/mysql/my.cnf` against 1 vCPU / 1200 MB container cap:

| Setting | Current | Problem | Suggested |
|---|---|---|---|
| `max_connections` | 50 | Real peak is <15 (5 php-fpm + queue + cron). Per-connection buffers ≈9 MB × 50 = ~450 MB on top of the 512 MB buffer pool, inside a hard 1200 MB cap Docker enforces with SIGKILL. | 20 |
| `max_user_connections` | 40 | same | 15 |
| `table_open_cache_instances` | 16 | Exists to shard the cache across CPU cores. You have one core. Fragments the budget for no gain. | 1 |
| `table_open_cache` | 4000 | Oversized for a few dozen tables | ~1000 |
| `performance_schema` | ON | Typically 100–150 MB fixed, inside the same cap | OFF unless actively used |
| binary logging | MySQL 8 default (ON) | `log_bin_trust_function_creators=1` at line 47 implies it. No replica, no PITR tooling anywhere in the repo — pure disk I/O and space cost. | `skip-log-bin` unless replication is planned |

`innodb_buffer_pool_size = 512M` is reasonable.

**`[VERIFIED] [ADDED IN REVISION 2]` The durability tuning cancels itself out.** Revision 1 described
`innodb_flush_log_at_trx_commit = 2` as trading durability for speed. Measured on the live server,
it buys nothing:

```
innodb_flush_log_at_trx_commit   2      ← "don't fsync the InnoDB log every commit"
log_bin                          ON
sync_binlog                      1      ← "DO fsync the binlog every commit"
```

`sync_binlog = 1` (the MySQL 8 default) forces a disk sync on every transaction commit, reinstating
exactly the per-commit fsync that `innodb_flush_log_at_trx_commit = 2` was set to avoid. You pay the
latency **and** accept the reduced InnoDB durability, gaining neither.

Since there is no replica and no PITR tooling anywhere in the repo, disabling the binlog resolves
both this and the disk-overhead point above in one change: add `skip-log-bin` to `my.cnf`. If you
ever do want PITR, the correct pairing is `innodb_flush_log_at_trx_commit = 1` with
`sync_binlog = 1` — not the current mix.

## 9. Performance and frontend

### 9.1 `[HIGH] [CORRECTED]` Sessions run on MySQL — but the cache is already on Redis

**`[CORRECTED]`** The agent read `.env.example` and `DEPLOYMENT_RUNBOOK.md` rather than production
and claimed `CACHE_STORE=database`. Your live `.env`:

```
SESSION_DRIVER=database      ← the real finding
QUEUE_CONNECTION=database
CACHE_STORE=redis            ← already correct
```

Confirmed with a live cache round-trip through the running app (`Cache::put`/`Cache::get` returned
`ok`, `cache.default = redis`).

What **is** true: every request — including the 60-second unread-count poll on every open tab
(`DashboardLayout.jsx:54-58`) — does a SELECT and UPDATE against the same MySQL instance that holds
the wallet ledger. On one vCPU that competes directly with money-path queries and InnoDB locks.

**Fix.** `SESSION_DRIVER=redis`. Redis is already running, already authenticated, and using 3.27 MB
of its 64 MB. **Keep `QUEUE_CONNECTION=database`** — durability matters more there than speed, and
Redis has no persistence configured.

### 9.2 `[MEDIUM] [VERIFIED]` The payments page ships an Excel library for a rarely-used button

The agent built the app to measure this — 180 JS chunks, 3.6 MB raw, ~152 KB CSS.

| Chunk | Raw | Gzip |
|---|---|---|
| `app-*.js` (every page, incl. login) | 308 KB | **102 KB** ✓ within budget |
| `PaymentsPage-*.js` | 413 KB | **126 KB** ← heaviest page |
| `generateCategoricalChart-*.js` (recharts) | 329 KB | 89 KB |
| `BigCalender-*.js` (react-big-calendar + moment) | 202 KB | 64 KB |
| `chart-*.js` (chart.js) | 175 KB | 61 KB |

CLAUDE.md's claim that `app.jsx` avoids importing `DashboardLayout` **holds** — verified.

`PaymentsPage.jsx:4` → `PaymentsList` → `TeacherEarningsTable.jsx:19-35`, which eagerly imports
`recharts` (a non-default tab) and `xlsx` (line 35, used only on export click). Only `PaymentForm`
is lazy on that page; `TransactionAnalytics`, `AdminEarningsSection`, `BatchPaymentForm`,
`RecurringTransactionsPage` and `TeacherEarningsTable` are all eager.

**Fix.** `React.lazy` the table in `PaymentsList.jsx:7`; `await import("xlsx")` inside the click
handler. Roughly halves the page for the common path.

**Also:** `SingleAssistantPage.jsx:3` statically imports `BigCalender` while the equivalent
`SingleTeacherPage.jsx:3` correctly lazy-loads it. One-line fix.

**Lower priority:** the app ships *two* charting libraries — `chart.js` in `SingleSchoolPage`,
`CashierPage`, `TransactionAnalytics`; `recharts` in 8 other files. Per-page splitting means neither
chunk doubles, but it is redundant dependency surface with no shared caching benefit. Worth
standardizing next time either is touched.

### 9.3 `[MEDIUM] [SOURCE]` `/message/{user}` loads entire conversation history

`MessageController.php:71-98`: `->orderBy('created_at','asc')->get()` — no limit, no pagination.
`InboxPopup.jsx:294-319` renders every row with no virtualization. A long-running staff conversation
holds one of only **five** php-fpm workers, and `->with(['sender','recipient'])` eager-loads two
relations whose values are already known (only two participants exist) for every row.

**Fix.** `->latest()->limit(50)->get()->reverse()->values()`, with a cursor for older messages.

### 9.4 `[MEDIUM] [SOURCE]` php-fpm pool has no elasticity and a 5-minute timeout

`pm = static` commits all 5 workers' memory permanently, even at 3 a.m. with zero traffic.
`request_terminate_timeout = 300s` with `fastcgi_read_timeout 300s`
(`docker/nginx/default.conf:129-130`) means one slow request occupies 1 of 5 workers for up to five
minutes — 2-3 concurrent slow requests could exhaust the pool and start 504ing other users.

**Fix.** Consider `pm = dynamic`. Confirm no endpoint routinely runs minutes; if any does, move it
to the queue.

### 9.5 `[LOW] [SOURCE]` O(n·m) lookups in a row renderer

`StudentListPage.jsx:252, 260` — `Alllevels.find(...)` and `Allclasses.find(...)` per row, per
render, against arrays already fully available. The table is server-paginated so the practical cost
is small.

**Fix.** `useMemo(() => new Map(Alllevels.map(l => [l.id, l])), [Alllevels])`, then O(1) `.get()`.

### 9.6 `[NOTE]` Inertia shared props — verified correct

`HandleInertiaRequests.php:106-136`: `chatContacts` (129), `unreadCount` (134), `flash.message`/
`flash.error` (117-120) are all closures — a partial reload with `only:` does not pay for them.
Matches CLAUDE.md's claim; no regression. `activeSchool` reads from an already-loaded session array,
correctly not a closure.

Only `'user' => $user` (113) is not lazy. It has `$hidden`, so no leak, and it is small — low
priority.

### 9.7 `[NOTE]` nginx — no changes needed except Brotli

gzip with a sane type list at `comp_level 5` (91-98), immutable 1-year asset caching plus
`open_file_cache` (94-99), 7-day cache for the storage alias (104-110), HTTP/2 (52),
`client_max_body_size 20M` (56), login rate-limited at `10r/m` with `burst=5 nodelay` (16, 83, 87).

**Only gap:** no Brotli. Typically 15-20% better than gzip on JS/CSS. Requires `ngx_brotli` compiled
into the image. Use `brotli_static on` with build-time pre-compression so there is no per-request
CPU cost. Worth doing on the next image rebuild; not urgent.

## 10. Code quality and maintainability

### 10.1 `[HIGH] [SOURCE]` `TeacherMembershipPaymentService.php` — 1,435 lines, correct but unmaintainable

The arithmetic is careful. The file is full of comments documenting real shipped bugs that were
fixed: percentage-overallocation guard (264-277), Carbon 3 sign bug (1218-1224), `DivisionByZeroError`
guard (943-949), duplicate-record identity fix (340-348). `TeacherPayoutTest.php` covers the sharp
edges. The problem is the next five years.

**One class does five jobs:** commission math (`totalAllocatedPercentage`, `processTeacherPayment`
188-385), record CRUD (`createNewRecord` 444-530, `updateExistingRecord` 535-751 — 216 lines), the
monthly cron (`processMonthlyPayments` 817-911), invoice-edit reconciliation
(`reconcilePaidMonthsForInvoice` 918-1061), reversal-on-delete (1211-1382). None are unit-testable
in isolation — every test needs Eloquent, a real DB and the full call chain.

**Two error conventions for one failure mode:** `processInvoicePayment` returns soft
`$result['errors']`, which `InvoiceController.php:234-241` immediately re-throws as `\Exception`.

**Dense formula-string logging:** e.g. `'total_teacher_amount_formula' => "($studentTotalPaidCumulative
× $teacherPercentage / 100)"` (335-337, 736-741). Useful for one historical incident; roughly
doubles the line count of every money method, permanently.

**Deliberate dead code:** lines 652-693 compute `$monthsCountForPastPayment`/`$pastMonthShare` then
explicitly do nothing with them ("Note: Past month payment is already included… No need to
duplicate"). Correct today, but the next reader will reasonably "fix" the missing wallet call.

**Suggested decomposition** (behaviour-preserving, one step per PR, in this order):

1. Extract `TeacherCommissionCalculator` — **pure, no DB**. Takes
   `(Offer, Membership, string $teacherSubject, float $studentPaid)`, returns
   `{percentage, totalAmount, immediateAmount, monthlyAmount}`. This is `totalAllocatedPercentage()`
   plus the math in `processTeacherPayment` (226-338) and `updateExistingRecord` (549-631). **The
   direct win: unit-testable without a database**, which nothing in this file currently is.
2. Extract `TeacherPaymentRecordRepository` for `createNewRecord`/`updateExistingRecord`/
   `cleanupDuplicateRecords`.
3. Move `processMonthlyPayments` into `MonthlyTeacherPayoutRunner`, invoked by the existing command.
4. Move `reconcilePaidMonthsForInvoice` + `reverseInvoicePayments`/`reverseTeacherPayment` into
   `InvoicePayoutReconciler`.
5. Then delete the formula log fields, replacing with one structured context object.

## 14. Revision history — what the peer review changed

### Where revision 1 held up

Both `[CORRECTED]` calls in §12 survived the independent check: `CACHE_STORE` really is `redis`, and

The review downgraded a multi-subject ledger collision from Critical to Medium on the grounds that

none had been checked. Where this document now says `[VERIFIED]`, it means reproduced on the running
